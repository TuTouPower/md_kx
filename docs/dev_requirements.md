# mdformat 二次开发需求

## 背景

mdformat（CommonMark 合规 Markdown 格式化器）用于统一仓库文档风格。实际使用发现若干问题，需二次开发解决。本文档只讲需求与验收标准，不涉及具体实现方案。

## 环境

- 本仓库：md_kx（mdformat 1.0.0 fork）
- 目标用户：依赖 mdformat 格式化 `.agents/skills/*/SKILL.md`、`AGENTS.md`、`docs/**` 等文档的仓库
- 文档特征：带 YAML front matter、含大量有序列表（步骤编号）、表格要求紧凑（不 pad 对齐）、列表缩进要求统一

## 需求

### 需求 1：支持 YAML front matter（不破坏）

**现状问题**：mdformat 默认不识别 YAML front matter。文档开头的 `---` 被当作分隔线（thematic break），导致 front matter 里的 `name:` / `description:` 被误解析成标题，整个 front matter 被破坏。12 个带 front matter 的 skill 文档全部受损。

**期望行为**：文档开头若为 YAML front matter（`---` 包裹），原样保留，不被格式化、不破坏、不变更内容。

**验收标准**：
- 输入带 YAML front matter 的文档，输出后 front matter 与输入完全一致（逐字节比对）。
- 无 front matter 的文档行为不变。

**补充**：官方无此能力，需内置实现，不依赖第三方插件。

### 需求 2：支持统一缩进宽度

**现状问题**：mdformat 遵循 CommonMark「marker 对齐内容」语义，不强制统一缩进。同一文档内出现 2/3/4/5/6 空格混用的嵌套列表缩进，mdformat 判定全部「合法」后不改动，导致文档缩进风格混乱。

**期望行为**：提供缩进宽度配置项，让嵌套列表缩进统一为指定宽度（本项目统一为 4 空格）。

**验收标准**：
- 新增配置项可指定统一缩进宽度（默认值不影响现有行为）。
- 设置后，文档内所有嵌套列表缩进统一为该宽度，无 2/3/5/6 等混用残留。
- 代码块（``` 围栏内）内容不被改动。

### 需求 3：保留有序列表编号语义

**现状问题**：mdformat 默认把所有有序列表项压成 `1.`（源码丢失真实编号）。文档里步骤编号是语义（如「步骤 4-6」的交叉引用），压平后无法从源码判断原编号。

**期望行为**：默认保留有序列表原有编号（或提供开关，打开后编号按自然顺序连续，从 1 开始递增）。

**验收标准**：
- 默认行为不改变源码编号（不把所有项压成 `1.`）。
- 或提供配置开关：开启后输出 `1.` `2.` `3.` 连续编号，关闭则保留原文编号。

### 需求 4：紧凑表格（不 pad 对齐）

**现状问题**：启用 GFM 表格支持后，mdformat 会把表格 pad 成对齐格式（单元格补空格对齐）。仓库要求表格紧凑（单元格不做空格 pad 填充）。

**期望行为**：表格保持紧凑，单元格不补空格对齐。

**验收标准**：
- 格式化后表格单元格不被 pad 对齐（`| a | b |` 不变成 `| a    | b   |`）。
- 表格本身语法正确，能被正常渲染。

## 约束

- 不改动代码块（围栏内）内容。
- 现有 CommonMark 合规性不回退。
- 插件机制保持向后兼容（若改动涉及插件接口）。
- 默认行为尽量不破坏现有已格式化文档。

## 验收方式

对下列样例逐项跑格式化并比对：

1. **front matter**：`---\nname: x\ndescription: y\n---` 开头文档 → front matter 原样保留。
2. **缩进**：含 2/3/5/6 空格混用嵌套列表的文档 → 统一为 4 空格（配置后）。
3. **编号**：`1.`~`7.` 有序列表 → 默认或开关下保留/恢复自然编号。
4. **表格**：`| a | b |` 表格 → 保持紧凑不 pad。
5. **代码块**：围栏内多行代码 → 内容零改动。

## 非目标

- 不做其他 Markdown 风格规则（如空行数量、标题大小写等）。
- 不重写现有渲染器架构，不引入新的依赖。
